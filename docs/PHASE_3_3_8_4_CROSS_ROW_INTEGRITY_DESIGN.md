# Phase 3.3.8.4 — Cross-row proposal/reservation integrity

**Decision:** Do not add a production constraint trigger under the current direct-write model. A deferred read-only validator can check a transaction's final visible rows, but it cannot prove correctness against concurrent direct SQL. Taking a proposal lock from a reservation trigger would invert the established lock order and can deadlock. Keep lifecycle enforcement in the application services pending the owner decisions and concurrency proof below.

**Scope and evidence:** This report inspects the current worktree, including the uncommitted `f8a3c9d2e641` migration. That migration introduces Phase 3.3.8.1 event immutability, Phase 3.3.8.2 submitted allocation-line insertion protection, and Phase 3.3.8.3 row-level lifecycle constraints. The older `c3d3f1a9b742` reservation foundation and `d7e4b8c2a913` proposal-version integrity migrations are prerequisites, not the source of those Phase 3.3.8 protections. The available repository history does not establish that 3.3.8.1–3.3.8.3 were reviewed and accepted. No PostgreSQL integration experiment was run: `TEST_DATABASE_URL` was not set as a process environment variable, and an isolated target was not independently verified. The companion [read-only diagnostic SQL](../prototypes/phase_3_3_8_4_candidate_audit.sql) is an unexecuted predicate prototype, not an enforcement claim. No migration, trigger, constraint, service, or development database was changed for this phase.

## 1. Verified service transitions and candidate invariants

The services acquire batch, order, proposal, line, then reservation locks through [`reservation_transaction.py`](../backend/app/reservation_transaction.py). Submission requires a nonempty line set, creates one `PENDING` reservation per line, and sets the proposal to `PENDING_APPROVAL` in one transaction ([`reservation_service.py`, submission](../backend/app/reservation_service.py#L352)). Approval requires exactly one reservation per line, changes all to `COMMITTED`, and sets `APPROVED` ([approval](../backend/app/reservation_service.py#L478)). Rejection and cancellation change all reservations to their matching terminal label ([termination](../backend/app/reservation_service.py#L613)). Expiry changes all `PENDING` reservations to `EXPIRED`; release changes all `COMMITTED` reservations to `RELEASED` ([expiry/release](../backend/app/reservation_service.py#L736)). Approved cancellation retains each reservation's `committed_at`: the termination loop changes status and terminal fields but does not clear that timestamp. All seven transitions in the request are present.

The following are **candidate persisted-state invariants**, conditional on approval to make the current service behavior database policy:

| Candidate | Exact predicate at a completed transaction | Existing protection / limit |
| --- | --- | --- |
| Draft reservation absence | If `proposal.status = DRAFT`, no reservation has its `proposal_id`. Drafts may have no lines and may gain lines. | Not currently enforced across rows. |
| Submitted structure | If status is not `DRAFT`, exactly one version exists, at least one line belongs to it, and every such line has exactly one reservation. | Version insert policy and immutability come from `d7e4b8c2a913`; reservation line uniqueness and composite foreign keys cover duplicates, wrong version and orphan rows, but not a missing reservation or an empty line set. |
| Lifecycle pairing | For a non-draft proposal, every reservation has the status shown below. The comparison is per row; it does **not** assert a universal one-to-one status mapping or infer the transition that produced `CANCELLED`. | Currently checked by services only. |
| Pending expiry snapshot | For `PENDING_APPROVAL`, each `PENDING` reservation has `expires_at IS NOT DISTINCT FROM proposal.expires_at`. The existing proposal check requires non-null expiry. | Checks do not compare rows. Do **not** require `expires_at > now()`; overdue pending rows are valid until expiry processing. |
| Cancel history uniformity | For a `CANCELLED` proposal, either all cancelled reservations have non-null `committed_at` or all have null `committed_at`. The former records approved cancellation; the latter records pending cancellation. Never clear a present `committed_at`. | This follows the two service source states, but requires owner approval as a database policy. |
| Event owner equality | If an event has `reservation_id`, its `proposal_id` and `proposal_version_id` equal those of the referenced reservation. A null `reservation_id` is valid. | Existing foreign keys independently validate the event's proposal/version and reservation existence, but do not relate their owners. Event rows are append-only if the uncommitted `f8a3c9d2e641` migration is applied. |

Current service pairing, with cancellation deliberately carrying two histories:

| Proposal | Reservation(s) | Proven source operation |
| --- | --- | --- |
| `DRAFT` | none | Draft persistence before submission |
| `PENDING_APPROVAL` | `PENDING` | Submit |
| `APPROVED` | `COMMITTED` | Approve |
| `REJECTED` | `REJECTED`, no `committed_at` | Reject pending |
| `CANCELLED` | `CANCELLED`, `committed_at` absent **or retained for all rows** | Cancel pending **or** approved |
| `EXPIRED` | `EXPIRED`, no `committed_at` | Expire pending |
| `RELEASED` | `RELEASED`, `committed_at` retained | Release approved |

The [`allocation.py` model](../backend/app/models/allocation.py) declares row checks, which model-based schema creation can include. The earlier `c3d3f1a9b742` migration defines reservation lifecycle timestamp checks; its presence in the migration chain does not establish which database has applied it. The Phase 3.3.8.3 `f8a3c9d2e641` migration defines the proposal pending/rejected/cancelled/released metadata checks and reservation rejected/cancelled reason check, but it is currently uncommitted in this worktree; deployment and acceptance have not been verified. Under those definitions, a `RELEASED` **proposal** requires a nonblank `terminal_reason_code`, while a `RELEASED` **reservation** requires `committed_at` and `terminal_at` and has no release-reason check. In a migration-managed database, rejected and cancelled reservations require a nonblank reason only if `f8a3c9d2e641` is applied. Expiry requires no terminal reason. The service currently copies terminal reason and some timestamps to every reservation, but exact cross-row equality of reason text and operation times is **not** included in the minimal candidate policy; that would need a separate owner decision. Likewise, a cancelled reservation's `committed_at` must remain meaningful even though its final status is `CANCELLED`.

## 2. Limits: what cannot safely be enforced now

* **A concurrent-safe nonempty cross-row assertion via a read-only deferred trigger under ordinary `READ COMMITTED`.** Two direct SQL transactions can each delete a different reservation and its line from a submitted two-line proposal. If their deferred reads occur before either commits, each can see its own deletion plus the other transaction's still-visible pair, pass, and then both commit leaving zero lines. The immediate reservation-to-line foreign key does not prevent deleting each reservation before its line. The Phase 3.3.8.2 draft-line *insert* trigger does not cover these deletes. This is a logically derived possible write-skew interleaving under the stated isolation and trigger assumptions, not an observed database experiment or test result. It violates the proposed nonempty-proposal invariant; it does not by itself violate the separate one-reservation-per-remaining-line rule.
* **Proposal/line/reservation consistency for arbitrary direct SQL while preserving the lock order.** A reservation-row trigger fires after the DML has taken its row lock. Acquiring a proposal, line, batch, or order lock then goes backwards. The same issue applies at deferred firing time because the transaction retains its earlier row locks.
* **Event completeness without new policy.** Services insert `proposal_generated`, `proposal_submitted`, `proposal_approved`, `proposal_rejected`, `proposal_cancelled`, `proposal_expired`, and `proposal_released` events, but the schema defines `event_type` as nonblank text, not a transition contract. Proposal-level events intentionally have null `reservation_id`. No requirement that every proposal state have one particular event, exactly one event, or one event per reservation follows from the current schema. An event may name a reservation only if its owner matches; that is referential consistency, not completeness.
* **Wall-clock expiry as a static invariant.** `PENDING` with a past expiry is explicitly permitted until the expiry service runs. The predicate `expires_at > now()` is unsuitable as a persistent check.
* **Historical transition legality from current row state alone.** A final `CANCELLED` row may have come from either pending or approved. Current-state checks cannot prove that the transition occurred through the service or that every intermediate event was recorded.
* **Universal protection from privileged SQL.** Table owners/superusers can change trigger definitions or disable enforcement; row triggers do not fire for `TRUNCATE`. A direct-write enforcement design must address table privileges and `TRUNCATE`, including `CASCADE`, explicitly.

## 3. Trigger timing and affected tables

An ordinary `CHECK` cannot reference another table row; PostgreSQL explicitly rules this out for a persistent cross-row guarantee ([constraint documentation](https://www.postgresql.org/docs/current/ddl-constraints.html)). The existing `UNIQUE` and foreign keys should remain the first line of defense for relationships they can express.

A minimal experimental design would use `AFTER INSERT OR UPDATE OR DELETE` **constraint triggers**, `DEFERRABLE INITIALLY DEFERRED FOR EACH ROW`, on `allocation_proposals`, `allocation_reservations`, and `allocation_lines`. The function must derive the affected proposal ID from `OLD` and `NEW` where necessary, then reread the *current* proposal/version/line/reservation set rather than trusting the queued row image. The proposal trigger covers status changes even if no reservation row is written. Reservation triggers cover insert, update, and delete, including same-status updates. Line triggers cover insertion, update, and deletion of the line set. The existing version triggers reject version update/delete and serialize version insertion on the parent proposal, so an additional version trigger is unnecessary for the current single-version policy; future relaxation would require coverage there too. A separate `BEFORE INSERT` event trigger could compare a non-null reservation's immutable owner IDs without requiring a row lock, but that candidate still needs an isolated concurrency test. `TRUNCATE` prevention or privilege removal would be separate statement-level protection; deferred row triggers cannot cover it.

For event-to-reservation ownership, an alternative candidate is a composite foreign key from `allocation_events(reservation_id, proposal_id, proposal_version_id)` to a corresponding unique key on `allocation_reservations(id, proposal_id, proposal_version_id)`. PostgreSQL's default `MATCH SIMPLE` allows a proposal-level event with null `reservation_id`, while requiring a matching owner when `reservation_id` is supplied ([foreign-key documentation](https://www.postgresql.org/docs/current/sql-createtable.html)). This is a design candidate for future evaluation, not a currently implemented constraint or an approved migration. Existing data and migration compatibility must be checked before implementation. It would enforce only event ownership; it would not solve proposal/reservation lifecycle consistency generally.

PostgreSQL permits deferred constraint triggers only as `AFTER ROW` triggers. Their `WHEN` expression is evaluated immediately, so a `WHEN` filter based on an intermediate status can accidentally omit a final-state check. `SET CONSTRAINTS` can also force queued checks earlier. These details follow the [PostgreSQL `CREATE TRIGGER` documentation](https://www.postgresql.org/docs/current/sql-createtrigger.html) and [PostgreSQL `SET CONSTRAINTS` documentation](https://www.postgresql.org/docs/current/sql-set-constraints.html). This timing handles multi-statement service transitions in one transaction, but timing alone does not serialize concurrent writers.

The diagnostic SQL prototype expresses the minimal candidate predicates and returns `(proposal_id, code)` rows for violations. It intentionally performs only `SELECT`; it does not create triggers or claim to close the concurrency gap. It relies on existing foreign keys and uniqueness constraints for some orphan and duplicate protections, so it is not a complete independent audit if those protections have been bypassed. Its table names are unqualified: before any eventual operational execution, the operator must verify the intended database and `search_path`. The query has not been executed.

## 4. Lock acquisition analysis

| Action | Lock order / effect | Finding |
| --- | --- | --- |
| Lifecycle and reservation-aware mutation services | `batches → orders → proposals → allocation lines → reservations`, with `FOR UPDATE` and rediscovery under parent locks | Cooperating operations serialize according to the existing protocol. |
| Deferred validation using ordinary `SELECT` | Existing transaction locks remain held; validation obtains no row-level lock on the related rows | No new DML row-lock inversion, but MVCC visibility permits the deletion write skew above. This is a diagnostic technique, not a correctness proof. |
| Reservation `INSERT` / `UPDATE` / `DELETE` trigger that locks proposal | The reservation write may already own a reservation row lock before the proposal lock is requested | Reverse edge `reservation → proposal`; conflicts with a service holding proposal and waiting for reservation. Deferral moves the request to transaction end but does not remove the held reservation lock. |
| Line trigger that locks proposal | A line update/delete may already own a line row lock | Reverse edge `line → proposal`; conflicts with service `proposal → line`. The existing **insert** trigger obtains batch, order, then proposal locks before the new line exists, which is materially different. |
| Existing reservation snapshot trigger | `BEFORE INSERT OR UPDATE` performs `SELECT ... FOR SHARE` on the line (`c3d3f1a9b742`) | A direct reservation **UPDATE** can already acquire `reservation → line`, opposite the service order. This pre-existing exposure needs its own review; adding another reverse lock worsens it. |
| Event owner comparison via plain `SELECT` | No requested row lock; existing foreign keys and immutable reservation snapshot fields supply reference stability in the current schema | Plausible narrow exception, but not a proposal lifecycle enforcement mechanism. Do not deploy without a test of insert/delete races. |

PostgreSQL documents that row-level deadlocks are possible and recommends a consistent acquisition order in its [explicit-locking guidance](https://www.postgresql.org/docs/current/explicit-locking.html). `READ COMMITTED` queries use statement snapshots; ordinary reads do not turn a deferred predicate into a serializable check ([transaction-isolation guidance](https://www.postgresql.org/docs/current/transaction-iso.html)). `SERIALIZABLE` with complete retries, or restricting all table writes to code that first locks the parents, could potentially support stronger enforcement, but both change the present write contract. Neither is proven by this report.

## 5. Concrete deadlock schedules and mitigations

The service lock order and the existing reservation snapshot trigger are source-level facts cited above. The schedules below are derived possible interleavings; no deadlock was reproduced or otherwise observed in a database experiment for this report.

1. **New reservation-to-proposal trigger:** T1 updates or deletes reservation R, holding R, then its deferred trigger waits for proposal P. T2 has P via the service protocol and waits for R. This forms a deadlock cycle that PostgreSQL would resolve by aborting a transaction, typically reported as `40P01`. Deferral does not change the cycle. **Mitigation:** no parent-locking trigger on reservation writes; make direct writes acquire P first through an enforced write API, or do not add the trigger.
2. **New line-to-proposal trigger:** T1 updates/deletes L, holding L, and waits for P. T2 holds P and waits for L. **Mitigation:** same parent-first write API, or no lock-taking line trigger.
3. **Existing snapshot trigger:** T1 directly executes an otherwise valid no-op `UPDATE allocation_reservations SET expires_at = expires_at WHERE id = R`, holding R, then waits for L in the existing `FOR SHARE` trigger. T2, having acquired P then L, waits for R while approving/cancelling/expiring/releasing or updating a related target. **Mitigation:** direct writers must follow parent-first locking; independently review the existing trigger if direct writes are part of the supported contract. Application retry classification already recognizes `40P01`, but retrying is recovery, not prevention.

## 7. Rollback behavior

A deferred trigger exception during `COMMIT` aborts the **whole transaction**, including proposal, reservations, lines, events, and idempotency rows written in it. The service's `session_factory.begin()` boundary is built to roll back on commit failure. A diagnostic `SELECT` has no rollback effect. In an experimental schema, `DROP TRIGGER` and `DROP FUNCTION` remove prototype enforcement; dropping them does not repair data already committed while they were absent or disabled. A future migration downgrade must remove only its own objects and leave the existing 3.3.8.1–3.3.8.3 constraints intact.

## 8. Migration strategy if approved later

1. Verify and record acceptance of 3.3.8.1–3.3.8.3, exact deployed schema, PostgreSQL version, and ownership of all direct writers. Resolve the policy decisions below.
2. Run the read-only audit against a snapshot of the intended production data; repair historical violations through reviewed data operations before adding enforcement.
3. Choose and prove an enforceable serialization contract: either make all writes, including direct SQL, use a parent-first controlled write API with appropriate grants, or move all relevant writers to `SERIALIZABLE` with full-transaction retries. Reconcile the existing reservation snapshot trigger's reverse lock path. A naked deferred trigger is insufficient.
4. In a **new** migration only after approval, install the smallest set of chosen schema-qualified constraints, functions, and triggers, include explicit `TRUNCATE`/privilege coverage where relevant, and keep a reversible downgrade. Do not edit existing revisions. Plan deployment locks and bounded migration timeouts.
5. Pass the complete matrix above on an independently verified isolated PostgreSQL database, then rehearse upgrade, rollback, and repeated upgrade with realistic data and concurrent service traffic. Reaudit immediately after rollout.

## 9. Owner decisions required

* Confirm that the prerequisite phases and the currently uncommitted `f8a3c9d2e641` migration containing 3.3.8.1–3.3.8.3 protections were reviewed and accepted.
* Approve whether the candidate status pairing, nonempty submitted line set, exactly one reservation per line, and uniform cancellation commit history are durable database policy rather than current service implementation details.
* Decide whether direct SQL writes remain supported. If yes, approve a controlled parent-first write interface and table privilege changes, or a universal `SERIALIZABLE`/retry contract. This phase authorizes neither change.
* Decide whether event-to-reservation owner equality should become a constraint. Separately define any event-type/completeness policy before attempting to require terminal events; current code alone does not authorize it.
* Decide whether to enforce cross-row equality of reason codes, reason text, and operation timestamps. Expiry must remain exempt from a required terminal reason, and approved cancellation must retain `committed_at`.

**Prototype finding:** The unexecuted read-only audit is designed to identify persisted contradictions for review. It cannot prevent the logically derived possible write-skew interleaving and is intentionally not installed. No concurrent failure or deadlock was observed in a database experiment. The safe production recommendation remains application-level lifecycle enforcement plus the existing parent-lock protocol until a new, approved write contract is proven.
