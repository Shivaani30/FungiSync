## 2. Recommended transaction contract

**Proposed policy:** one complete draft creation operation creates proposal P, version 1, the entire allocation-line set (possibly empty), and its initial event in one caller-owned transaction. Committed DRAFT proposals are not reopened for line creation. Changing a draft means creating a new proposal, consistent with the single-version/no-revision policy. This is a deliberate narrowing of the current direct-SQL ability to append lines to any DRAFT; owner approval and historical-data review are required.

The application calls the writer **once in a fresh transaction**, performs no earlier lock-taking DML in that transaction, and never silently falls back to ORM/direct line insertion. One non-superuser application runtime login serves draft creation and lifecycle requests. It has no direct allocation-line INSERT, UPDATE, DELETE, or TRUNCATE privilege. The database additionally rejects a second writer invocation in the same top-level transaction, even if it names another proposal. A savepoint rollback that undoes the first invocation also undoes its guard; a later attempt is then a new effective attempt in that transaction. This guard does **not** detect unrelated parent-row DML before the first writer call; the fresh-transaction call contract must be enforced by the application adapter and tested.

This contract preserves zero-line DRAFT creation but seals it immediately: later lines require a new proposal. Existing committed DRAFT rows, including zero-line historical rows, remain readable and are not edited by the writer. The submission service rejects empty line sets ([`test_zero_line_draft_cannot_be_submitted`](../backend/tests/test_proposal_submission.py#L153)); historical zero-line DRAFTs therefore cannot be submitted under current behavior and cannot receive lines under the new contract. A replacement proposal is the supported route. Existing populated DRAFTs may still be submitted if otherwise eligible.

## 3. Controlled interface and complete-set guard

Recommend one `SECURITY DEFINER` function in a private, trusted schema, conceptually `allocation_private.create_complete_advisory_draft(order_id uuid, proposal_id uuid, version_id uuid, lines jsonb, exclusion_batch_ids uuid[], total_proposed_kg numeric, unfulfilled_kg numeric, ruleset_version text, event_metadata jsonb)`. It returns exactly one record `(proposal_id uuid, proposal_version_id uuid, line_ids uuid[], event_id uuid)`, including an empty `line_ids` array for a zero-line draft. All IDs are supplied/generated once before insertion and returned in input order. This is an interface proposal, not executable SQL or an approved signature.

The function must:

1. Insert `txid_current()` into a private migration/admin-owned `allocation_private.draft_write_tx_guard(txid bigint PRIMARY KEY, created_at timestamptz)` **before any parent-row lock**. On a same-transaction conflict, raise a stable application-mapped error immediately. The table is not writable or readable by the runtime login; the function owner receives only its needed guard-table INSERT privilege. Guard insertion rolls back with the transaction; committed rows remain until privileged manual maintenance removes them. PostgreSQL 13 exposes `txid_current()` ([transaction-ID documentation](https://www.postgresql.org/docs/13/functions-info.html)). A caller-controlled GUC, advisory lock, or writable temporary table is not an equivalent guard.
2. Validate the *whole* JSON input in memory before inserting any line: array/object shape and allowed keys, UUID casts, unique proposal/version/line IDs, unique line batch IDs as in the current persistence API, line order ID equal to the supplied order ID, positive finite decimal quantities with the current Python rule of **at most three fractional digits, even if extra digits are trailing zeros**, and maximum `999999999.999`, exact sum equal to `total_proposed_kg`, nonnegative unfulfilled quantity, and safe event metadata shape/size. Bind values; do not assemble dynamic SQL from input. Represent decimal quantities as strings until their original scale is checked and they are cast to unbounded `numeric`; never coerce through floating point or `NUMERIC(12,3)` before validation. Empty lines are valid only with zero proposed quantity.
3. Derive the union of line and exclusion batch IDs, deduplicate and sort UUIDs, then request **one `FOR UPDATE` batch row lock at a time in that order**. Do the same for all referenced order IDs (the current API has one). Check the locked-record persistence rules in Section 3.1: order and referenced-batch existence, eligible statuses, each line quantity against its batch's confirmed quantity, and `total_proposed_kg + unfulfilled_kg = locked order.quantity_kg`. The Python adapter may retain early validation but the function must not trust it. Do not silently turn advisory-only evaluator exclusions into new persistence rejections. Do not rely on JSON order or a set-based `UPDATE`/planner order as the lock-order proof.
4. Only after all batch and order locks, check/lock the proposed proposal identity. If an existing P is found, inspect status, version, existing lines, and reservation history for a precise error and **reject it regardless of DRAFT status**. This is the enforcement of no revision; no committed proposal is appended. For a fresh P, insert DRAFT P and version 1; their ownership/version rules are rechecked through the existing constraints and triggers. The newly inserted P is already locked by this transaction. A concurrent identical UUID insert may wait on a uniqueness check, but both legitimate writer calls have completed their parent locks before reaching it.
5. Insert every line in **ascending line UUID order**, irrespective of input order, so conflicting unique identities cannot invert line lock order. The function has already locked every referenced batch/order before the proposal/line phase; FK checks and the version trigger therefore cannot introduce a new wait for a lower-category parent. Build the initial `proposal_generated` event details from the validated line set and validated advisory flag, order ID, ruleset version, totals, warnings, order exclusions, and batch exclusions, insert the event in the same transaction, and return IDs. Any error aborts the call; the caller's transaction rolls back P, V, lines, event, and guard together. The function never commits.

The guard is needed even though an existing proposal ID is rejected: two calls in one transaction could otherwise create *different* proposals and acquire a new batch after retaining the first proposal lock. A private guard table gives a transaction-wide, database-enforced early rejection. A per-proposal seal would prevent repeated writes to P but still allow a second call for P2 after P1's locks; a documented one-call convention would not be enforced by the database. A predeclared transaction-wide target manifest could allow multiple calls, but needs additional private state, validation, and a larger API for a behavior the current application does not use. Temporary tables require additional ownership/spoofing proof; transaction GUCs are caller-changeable. Guard cleanup must never delete an active transaction's row; conservative retention is safe for correctness, though not for storage indefinitely.

### 3.1. Source-to-writer validation parity

The evaluator computes advisory eligibility **before** persistence takes locks. The current persistence gate checks only a subset again **after** batch/order locks; submission later applies the evaluator's full order/batch exclusions under its own locks ([`_ensure_submission_eligibility`](../backend/app/reservation_service.py#L316)). The controlled writer must reproduce the current persistence gate exactly to preserve draft behavior. “Before” in the table means evaluator or `_validate_result_shape` before the persistence transaction; “after” means current `persist_advisory_draft` after parent locks. An advisory exclusion is not itself a database rejection rule.

This matrix exposes a policy boundary: copying every evaluator exclusion into the writer would strengthen draft acceptance rules and can reject a result that current persistence accepts. The recommendation is exact **persistence** parity plus the existing submission revalidation, with the evaluator remaining the advisory source. If the owner instead requires database-level species/grade/date/price eligibility at draft creation, that is a separate business change; Unicode species matching is the clearest unresolved SQL-parity issue.

## 4. Derived lock schedules and limits

These schedules are logical consequences of the proposed permissions and function order. No concurrency test or deadlock reproduction was run in this design phase. `B`, `O`, `P`, `L`, and `R` denote batch, order, proposal, line, and reservation row locks. The private guard insert is in a table that lifecycle services never lock.

| Case | Schedule and retained locks | Wait and conclusion under the proposed contract |
| --- | --- | --- |
| A. New P vs another proposal operation | T1 guard → all B ascending → all O ascending → INSERT P → V → L ascending → event. T2 cannot discover T1's uncommitted P/V/L under ordinary committed reads. | T2 cannot hold or wait for that new P by its identity through normal lifecycle discovery before T1 commits. A guessed-UUID privileged operation is outside the runtime role contract; tests must also examine a duplicate supplied UUID. |
| B. New P vs overlapping targets | T2 lifecycle takes B ascending, O ascending, its visible P, L ascending, R ascending. T1 takes its complete B/O set before creating P. | T1 may wait for T2's B/O; T2 may wait for a B/O held by T1. With the same per-category UUID order neither can retain a later-category lock while requesting an earlier one. T1's P/L are newly created and unavailable to T2 until commit. |
| C. Existing DRAFT vs submission | T1's writer call for existing P takes its required B/O locks and then P, detects the existing P, and rejects; an early plain read may reject sooner. T2 submission takes B/O before P and requires at least one existing line. | Either T1 waits on B/O/P held by T2 or T2 waits on B/O/P held by T1; neither requests a lower-category lock afterward. If P has zero lines, service submission fails; if it has lines, writer rejects existing P. No successful append/submission race exists. |
| D. Two complete-set writers | T1 and T2 each register distinct txids, sort reverse-supplied overlapping batches to the same UUID order, then orders; each creates a new P and inserts lines by line UUID. | One may wait on a shared B, O, or duplicate UUID identity. The holder has no later B/O request. Unique-ID collisions fail or wait/resolve without a reverse row-lock edge. Both may succeed for distinct proposal/line IDs; no duplicate/missing lines within either committed proposal. |
| E. Repeated call, same or different P | T1's first call retains B/O/P/L and its guard row. Its second call attempts the same txid guard insertion **first**. | The second call raises before reading/locking any new B/O/P/L. This is the transaction-wide protection missing from a per-proposal seal or a single-call convention. |
| F. Direct line SQL | The single runtime login has approved function EXECUTE but no line INSERT/UPDATE/DELETE/TRUNCATE, table ownership, or owner-role membership. | PostgreSQL rejects direct line DML before trigger logic can be used as a bypass. A superuser/migration identity remains operationally privileged and is outside this claim. |

Proof assumptions requiring integration tests: the application really uses the restricted runtime login; no other executable routine exposes line DML; the draft adapter starts a fresh transaction and calls the writer before unrelated DML; lifecycle services continue the source-level parent-first order; all line-creating function paths use the guard and sorted loop; and trusted schema/trigger search paths are hardened. Sorting one function's input does **not** make arbitrary SQL transactions globally ordered. Because the same runtime login must have direct `UPDATE` on batches/orders/proposals for existing lifecycle and CRUD paths, it could issue `UPDATE P_old` (retain P), then call the writer needing `B_low`, while T2 holds `B_low` and waits for `P_old`: a possible deadlock. This is derived, not reproduced. The guard cannot reject that first writer call. The one-login design guarantees database denial of direct line writes and ordered **cooperating application** writer calls; it does not guarantee a universal lock order against arbitrary SQL executed with that login. Existing direct reservation writes may still invert line/reservation locks through the snapshot trigger; this design does not claim to solve all lifecycle deadlocks or cross-row integrity.

## 5. Roles, grants, and function security

The following are **three proposed identities**, not existing accounts or credentials. One non-superuser application login is sufficient for the current draft and lifecycle services **under their transaction contract**; its necessary parent/proposal `UPDATE` grants are the exact privilege combination that prevents a stronger arbitrary-SQL lock-order claim.

| Principal | Intended permissions | Explicit exclusions |
| --- | --- | --- |
| Application runtime login (non-superuser) | `CONNECT`, necessary schema `USAGE`, reviewed `SELECT`/CRUD/lifecycle table grants, and `EXECUTE` on **only** the approved complete-draft writer and line-lock helper. | No allocation-line INSERT/UPDATE/DELETE/TRUNCATE, guard access, schema/function ownership, schema `CREATE`, membership in function-owner or migration/admin roles, or other executable line writer. |
| Function owner (NOLOGIN) | Owns only the controlled writer, line-lock helper and reviewed hardened reservation-snapshot trigger function. Receives only exact table/column grants needed for their bodies: writer P/V/L/event/guard INSERT and B/O/P locking; line helper line SELECT and minimum column-level UPDATE for `FOR UPDATE`; snapshot function line SELECT and minimum column-level UPDATE for `FOR SHARE`. | Not a table owner (including the guard table), login, superuser, or migration identity; no unrelated table DML. PostgreSQL requires `UPDATE` privilege on at least one selected column for row-locking SELECT ([`SELECT` documentation](https://www.postgresql.org/docs/13/sql-select.html)). |
| Migration/admin login | Owns or manages protected tables and trusted schemas, applies migrations and grants, and performs guarded test setup through a separate connection. | Never used by normal application requests; credentials unavailable to runtime workers. |

The current generic CRUD routes/service ([`api/routes/crud.py`](../backend/app/api/routes/crud.py#L7), [`services.py`](../backend/app/services.py#L8)) require direct create/update/delete rights on growers, buyers, batches, and orders; reservation-aware batch/order PATCH uses the same request bind ([`reservation_mutations.py`](../backend/app/api/routes/reservation_mutations.py#L19)). A provisional **single-runtime** grant inventory is: core CRUD tables `SELECT/INSERT/UPDATE/DELETE`; proposals `SELECT/UPDATE`; versions `SELECT`; lines `SELECT` plus helper EXECUTE; reservations `SELECT/INSERT/UPDATE`; events `SELECT/INSERT`; idempotency `SELECT/INSERT`; writer EXECUTE. No current lifecycle path found needs direct line DML or direct proposal/version INSERT. Audit exact columns, dependencies, and every API endpoint before issuing grants. The runtime's parent/proposal UPDATE privileges are needed by existing services but permit a hostile or buggy direct-SQL transaction to violate the service lock protocol; this is a deadlock/availability risk, not a bypass of line-DML denial.

The lifecycle service currently calls `SELECT ... FOR UPDATE` on lines ([`lock_allocation_lines`](../backend/app/reservation_transaction.py#L130)), and the reservation snapshot trigger calls `FOR SHARE` on lines on each reservation write ([`c3d3f1a9b742`](../backend/alembic/versions/c3d3f1a9b742_add_reservation_data_foundation.py#L138)). Both need `UPDATE` privilege on a line column under PostgreSQL 13; granting that directly to runtime would violate the no-direct-UPDATE requirement. A later migration must provide a narrow, reviewed **line-lock helper** executable by runtime after parent locks and harden the reservation snapshot trigger as a narrowly owned `SECURITY DEFINER` function. The application must replace its direct line `FOR UPDATE` query with that helper and then reread locked lines. Its line-lock order, snapshot behavior, and error mapping require dedicated tests. The helper must only lock supplied existing line IDs in ascending UUID order, return/verify all requested IDs, and never modify line values. The snapshot trigger must retain its existing line/version/target checks and `FOR SHARE` behavior. Neither helper gives arbitrary direct SQL a universal lock-order guarantee.

The writer, line-lock helper, and hardened snapshot-trigger function must set a fixed `search_path` with `pg_catalog` first, the trusted application schema next, and `pg_temp` last; fully qualify application objects and avoid dynamic SQL. Existing version/reservation trigger functions use unqualified names, so the application schema must be made trusted (including review/revocation of untrusted `CREATE` rights, notably for `public` on PostgreSQL 13) or those functions must be hardened in the **new** migration. PostgreSQL specifically warns about temp-schema masking in `SECURITY DEFINER` functions ([function guidance](https://www.postgresql.org/docs/13/sql-createfunction.html)). Revoke default `PUBLIC EXECUTE` on each privileged function in the same migration transaction, grant only the named runtime role on the writer/helper, and review default privileges for future functions. No runtime role may be a member of an owner/migration role, even with `NOINHERIT`, because membership can permit `SET ROLE`. Audit inherited grants, schema `CREATE`, table DML, `TRUNCATE`, trigger/function alteration, and callable routines before cutover. Allocation tables use UUID IDs, so this path needs no sequence grant; any introduced sequence must be reviewed separately.

### 5.1. Manual guard maintenance

No background worker is proposed. The migration/admin operator must (1) stop or drain draft-writer requests and prevent new draft requests from entering, (2) confirm no draft-writer transaction remains active, including idle-in-transaction sessions, (3) in one privileged maintenance transaction acquire `ACCESS EXCLUSIVE` on the private guard table and only then delete completed guard rows, and (4) commit before re-enabling draft creation. Use a bounded `lock_timeout`; if the lock cannot be acquired, abort cleanup and keep draft creation drained while investigating. `ACCESS EXCLUSIVE` conflicts with the writer's guard-table `INSERT` `ROW EXCLUSIVE` lock, which is held to transaction end. Once the maintenance lock is acquired, no transaction that has inserted a guard row can remain open, and a newly starting writer cannot insert its guard until cleanup commits. This is the database fence behind the quiescence check; deleting by an age threshold or `created_at` alone is unsafe. An already-started writer that has not yet inserted a guard waits at the table lock and can register after cleanup. Keep the guard private and make maintenance a documented admin-only operation with timeout, audit logging, and row-count/bloat monitoring.

## 6. Application and environment integration

Keep the public `persist_advisory_draft` signature and result type. Its future adapter should retain pure Python shape/Decimal validation, bind a single function call with the complete lines and exclusion IDs, map documented SQLSTATEs to current domain errors, and return the function's IDs. The function performs the authoritative locked revalidation and inserts P/V/L/event; the adapter must not pre-insert P or V, perform ORM line insertion, or fall back to a superuser connection. A fresh `session_factory.begin()` remains the transaction boundary. Changing this internal flow is necessary because letting the app create P before a function newly locks B/O would leave an unproved lock-order path.

Keep one application `DATABASE_URL`, but point it to the **non-superuser runtime** login for draft, lifecycle, and API operations. Add a separately configured migration/admin URL (name to approve), consumed only by Alembic and guarded test setup; it must never be used by request handling. `db/session.py` can retain one runtime engine/session factory; `alembic/env.py` must use only the migration URL. Verify runtime role attributes and effective grants at startup/deployment, and fail closed if the URL resolves to a superuser, owner, or role with direct line DML. The current shared single URL cannot satisfy this separation unchanged. Health checks should use the runtime connection. Do not store secrets in source or infer a secret manager from current files.

Local development needs explicit role bootstrap and runtime/migration placeholders in `.env.example`; Docker Compose's `POSTGRES_USER` bootstrap alone is insufficient and existing volumes do not rerun initialization scripts. Test needs a **dedicated isolated cluster** for role creation because PostgreSQL roles are cluster-wide and the currently configured test/development databases share a cluster. Production needs operator-managed role provisioning, secret distribution/rotation, migration credentials separate from process credentials, active-session checks, and documented grant audits. README/deployment instructions must be updated only in the implementation phase.

## 7. Migration, cutover, and rollback plan

Do not rewrite `c3d3f1a9b742`, `d7e4b8c2a913`, or the currently untracked `f8a3c9d2e641`. After confirming their acceptance/deployment, create **new** revisions:

1. **Preflight/bootstrap:** operator provisions the runtime login and NOLOGIN function owner under the separate migration/admin identity; migration checks their existence, attributes, non-membership, table ownership, trusted schema permissions, and expected revision. ## Hackathon-scope implementation decisions

**Recommended architecture for implementation planning:** use exactly three identities: one non-superuser application runtime login for draft creation, lifecycle and APIs; one NOLOGIN, non-table-owning function owner for the reviewed privileged functions; and one separate migration/admin identity for schema ownership, grants, maintenance and test setup. The runtime cannot directly write allocation lines and cannot inherit owner/admin privileges. The complete-draft writer takes the whole line set once in a fresh application transaction, registers `txid_current()` before parent locks, locks deduplicated batches and orders by UUID, creates P/version 1/lines/event atomically, and rejects any existing proposal or second effective call. Its SQL validation matches the current persistence gate in Section 3.1. The line-lock helper and hardened reservation snapshot trigger preserve lifecycle behavior without direct runtime line `UPDATE`. This is a recommendation, **not** owner approval to implement, migrate, or grant privileges.

**Owner decisions still required:** approve one-call/zero-line sealing and replacement-proposal policy; accept that the single runtime's necessary batch/order/proposal `UPDATE` grants leave a possible lock-order inversion for arbitrary direct SQL although the controlled application path is ordered; confirm advisory-only evaluator exclusions remain advisory at draft persistence (or separately approve a changed eligibility policy); approve the three-identity grant contract, private guard maintenance runbook, isolated test cluster, and gated cutover/rollback. If universal deadlock freedom for arbitrary runtime SQL is a requirement, this three-identity design cannot establish it without narrowing parent write privileges or controlling all lifecycle writes through further functions; that requirement would block implementation and needs a separate owner decision. No additional role is proposed absent that decision.

**Exact implementation sequence after approval:** (1) provision and independently verify isolated test roles/cluster, then production role attributes and trusted schema; (2) add a new gated migration for the private guard, owned functions, least grants, `PUBLIC EXECUTE` revocation, dependent trigger hardening and helper, preserving the historical revisions; (3) test exact validation parity, security, row locks, and quiescent guard cleanup on restricted connections; (4) adapt draft persistence to one writer call in a fresh transaction and lifecycle line locking to the helper, retaining current public return/errors; (5) drain old privileged runtime sessions, deploy separate runtime/migration URLs, verify actual role and direct line-DML denial, then replace the unsafe per-row parent-lock trigger with reviewed validation-only protection; (6) run focused and full regressions and retain the fail-closed rollback route in Section 7. Do not remove the unsafe trigger while an unrestricted runtime still writes lines.

**Minimum release tests:** real non-superuser runtime direct INSERT/UPDATE/DELETE/TRUNCATE denial and approved writer/helper success; public EXECUTE denial; exact evaluator-versus-persistence parity including Unicode species and historical zero-line behavior; second writer call in one transaction before new target locks; reverse-ordered and overlapping multi-line writers; writer versus submission and shared-parent lifecycle operations with observed waits; rollback after a mid-write error; guard cleanup waiting for an active writer; and event/version/snapshot/lifecycle regression tests. Tests need independent transactions and observed blocking or barriers, never sleeps alone. None were run for this design refinement.

**Unresolved blockers before deployment:** the existing f8 trigger still has the multi-line lock inversion, the observed test connection is a superuser in a cluster shared with development, role/grant deployment is unconfigured, and concurrency/privilege tests remain unexecuted. These block Phase 3.3.8 acceptance and production enforcement, but do not prevent implementing and testing the scoped design after the owner decisions above.
